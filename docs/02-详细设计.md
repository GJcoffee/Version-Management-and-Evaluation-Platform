## 3. 存储设计

### 3.1 SQLite 配置

```
PRAGMA journal_mode = WAL;
PRAGMA synchronous  = NORMAL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
```

- **单写连接**：所有写操作通过一个专用的写连接，由 `asyncio.Lock` 串行化；读操作使用连接池（大小 8）。
- 事件写入采用批量方式，见 7.3 节。

### 3.2 ID 规范

使用 ULID（按时间有序）加类型前缀：

| 前缀 | 实体 | 前缀 | 实体 |
|---|---|---|---|
| `agt_` | Agent | `ses_` | Session |
| `drf_` | Draft | `trn_` | Turn |
| `ver_` | Version | `evb_` | EvalBatch |
| `ast_` | Asset | `evr_` | EvalRun |
| `arv_` | AssetRevision | `evi_` | EvalItem |
| `cas_` | EvalCase | `cmp_` | CompareGroup |
| `prv_` | Provider | `job_` | Job |

### 3.3 表结构（DDL）

### 3.4 BlobStore

- 路径：`{data_dir}/blobs/{hash[0:2]}/{hash[2:]}`；
- 写入：先计算 sha256 → 已存在则直接返回 → 否则写临时文件，`fsync` 后原子重命名（`os.replace`）→ 写入 `blobs` 表；
- 引用计数：AssetRevision 新增时 +1；事件中的大 payload 也会 +1；删除会话或评测时 -1；
- GC（`POST /system/gc` 或 `evalp gc`）：删除 `refcount=0` 且创建时间超过 24 小时的 blob；同时清理已软删除且没有被任何版本引用的资产修订。

## 4. AgentSpec 与版本

### 4.1 配置型 Spec（`kind: config`）

```yaml
schema: evalp/v1
kind: config
model:
  provider: deepseek            # providers.name
  name: deepseek-chat
  params:
    temperature: 0.3
    top_p: 1.0
    max_tokens: 4096
    seed: 42                    # 可选，透传给支持 seed 的服务
prompts:
  system: asset://prompt/cs-system@latest   # 也可以直接写多行文本 (inline)
  variables:                                # Jinja2 变量
    company: 示例公司
tools:
  - asset://tool/query-order@3
  - builtin: knowledge_search
    with:
      sources: [asset://knowledge/faq@latest]
      top_k: 5
knowledge:
  inject:                                   # 全文注入，模板中用 {{ knowledge["style-guide"] }} 引用
    - asset://knowledge/style-guide@latest
runtime:
  max_steps: 12                 # 单轮内 LLM 调用次数上限
  turn_timeout_s: 180
  parallel_tool_calls: true
  tool_timeout_s: 30
```

### 4.2 代码型 Spec（`kind: code`）

```yaml
schema: evalp/v1
kind: code
transport: http                 # http | subprocess
http:
  base_url: http://127.0.0.1:8001
  headers:
    Authorization: "Bearer ${env:MY_AGENT_TOKEN}"   # 环境变量引用，原样参与哈希，不保存实际值
  timeout_s: 300
subprocess:                     # transport=subprocess 时使用
  command: ["python", "-m", "my_agent.evalp_entry"]
  cwd: "."                      # 相对 .evalp.toml 所在目录，发布时转为绝对路径
  env: {LOG_LEVEL: info}
source:
  repo: "."
  capture_git: true
  allow_dirty: false            # 为 true 时，把 git diff 存为 blob，补丁哈希参与 spec_hash
params:                         # 原样透传给 agent，作为版本差异的一部分
  retrieval_top_k: 8
  model: qwen-max
runtime:
  turn_timeout_s: 300
```

### 4.3 引用语法

| 写法 | 含义 | 允许出现在 |
|---|---|---|
| `asset://{kind}/{name}@latest` | 最新修订 | 只能出现在草稿中 |
| `asset://{kind}/{name}@{rev}` | 指定修订 | 草稿和版本 |
| `file:relative/path` | 工作区本地文件，push 时转成资产 | 只能出现在工作区的 `agent.yaml` 中 |
| `${env:NAME}` | 运行时读取的环境变量 | 任意字符串字段 |

### 4.4 发布算法

```python
async def publish(draft_id, expected_revision, notes, via) -> PublishResult:
    async with write_lock:
        draft = repo.get_draft(draft_id)
        if draft.revision != expected_revision:
            raise Conflict("DRAFT_CONFLICT")
        spec = AgentSpec.model_validate(draft.spec)          # 1. 结构校验
        await validate_semantics(spec)                       # 2. 业务校验：provider 和模型存在、资产存在、工具 schema 合法
        resolved, refs = resolve_refs(spec)                  # 3. @latest → @rev，同时记录每个修订的内容哈希
        if spec.kind == "code" and spec.source.capture_git:
            resolved.source = capture_git(spec.source)       # 4. 采集 commit、branch、dirty；dirty 且不允许时报错 GIT_DIRTY
        canonical = canonicalize(resolved)                   # 5. 规范化
        spec_hash = sha256(b"evalp/v1\n" + canonical)
        if existing := repo.find_version(draft.agent_id, spec_hash):
            return PublishResult(version=existing, existed=True)
        v = repo.insert_version(seq=next_seq, spec_hash=spec_hash, spec=resolved,
                                parent=draft.base_version_id, ...)
        repo.insert_asset_refs(v.id, refs)
        draft.base_version_id = v.id
        return PublishResult(version=v, existed=False)
```

**规范化规则**（保证哈希稳定，规则有单测 golden 文件锁定）：

1. 用 Pydantic 补齐所有默认值后再导出（`exclude_none=False`），这样"显式写了默认值"和"没写"得到相同的结果；
2. 资产引用替换为 `{"$asset": {"kind","name","rev","hash"}}`，哈希中包含内容哈希；
3. JSON 键排序，`separators=(",",":")`，`ensure_ascii=False`；
4. 浮点数用 `repr` 规范化，`1.0` 和 `1` 统一处理；
5. 内联文本统一换行符为 `\n`，并去掉行尾空白；
6. 以下字段不参与哈希：`notes`，以及显示用的 `name` 和 `description`。

### 4.5 版本 Diff

输入两个版本已固化的 Spec，展开资产内容后递归比较：

- **字典**：按键比较，结果为 add / remove / replace；
- **列表**：如果元素有身份键（tools 按工具名；knowledge 按资产名），按身份键匹配；没有身份键时按下标；
- **文本**：多行或超过 80 个字符的字符串，额外生成 unified diff；
- **资产**：哈希相同表示未变化；不同时标记为 `asset_changed`，如果是文本类资产，同时附上内容 diff。

```json
{
  "left":  {"id": "ver_…", "seq": 12, "spec_hash": "…"},
  "right": {"id": "ver_…", "seq": 13, "spec_hash": "…"},
  "changes": [
    {"path": "model.params.temperature", "op": "replace", "left": 0.3, "right": 0.7},
    {"path": "tools[query-order]", "op": "asset_changed",
     "left": {"rev": 3}, "right": {"rev": 4},
     "content_diff": {"format": "unified", "text": "@@ -3,7 +3,8 @@ …"}},
    {"path": "prompts.system", "op": "asset_changed", "left": {"rev": 5}, "right": {"rev": 7},
     "content_diff": {"format": "unified", "text": "…"}}
  ],
  "summary": {"add": 0, "remove": 0, "replace": 1, "asset_changed": 2}
}
```

前端在 Monaco DiffEditor 中显示两侧的完整文本；JSON diff 结果用来生成左侧的"变更导航"。

### 4.6 标签与回滚

- `POST /versions/{id}/tags {tag}`：把标签指向这个版本（UPSERT，同一个标签会从旧版本移过来）；
- `POST /versions/{id}/to-draft {draft_name?}`：用这个版本的 Spec 覆盖草稿（或新建草稿），把 `@rev` 保持原样，`base_version_id` 设为该版本。

### 5.1 各类资产的内容格式

|---|---|---|
| prompt | Markdown / 纯文本（Jinja2 模板） | 模板语法可以解析；列出用到的变量 |
| tool | YAML/JSON，见 5.2 | `parameters` 是合法的 JSON Schema；`impl` 类型合法 |
| knowledge | Markdown / TXT / JSONL（`{id,text,meta}`） | 大小 ≤ 20MB |
| dataset | JSONL / CSV，见 5.3 | 逐行校验，警告写入 `meta.schema_warnings` |
| file | 任意 | 大小 ≤ 100MB |

### 5.3 数据集格式

每行（JSONL）或每条记录（CSV 按列映射）：

```json
{
  "case_key": "refund-001",
  "input": "我要退货，订单 A001",
  "expected": "应说明退货流程并查询订单状态",
  "rubric": "提到 7 天无理由；调用了 query_order",
  "tags": ["refund", "p0"],
  "metadata": {
    "variables": {"company": "测试公司"},
    "tool_mocks": {"query_order": [{"match": {"order_id": "A001"}, "output": {"status": "已签收"}}]}
  }
}
```

- `input` 可以是字符串（单轮），也可以是 `["第一句", "第二句"]`（多轮，按顺序作为用户输入）；导入时统一为 `{"turns": [...]}`；
- 缺少 `case_key` 时，用 `sha256(input)[:12]` 自动生成，并给出警告，提示跨修订对比可能对不上；
- `metadata.tool_mocks`：这个用例运行时覆盖对应工具的实现，保证评测结果可复现；
- CSV 导入时需要提供列映射：`{"input":"问题","expected":"参考答案","tags":"标签(;分隔)"}`。

### 5.4 资产服务规则

- 新建修订时，内容哈希与已有修订相同则不新建，直接返回已有修订（`existed=true`）；
- 删除：如果有版本引用（`version_asset_refs`）或评测引用，只能软删除，列表默认不显示；
- 修订 diff：`GET /assets/diff?left=arv_x&right=arv_y`，文本类资产返回 unified diff；数据集返回按 `case_key` 统计的增加、删除、修改的用例数及明细。

## 6. 运行时

### 6.1 消息模型

```python
class ToolCall(BaseModel):
    id: str
    name: str
    arguments: dict | str              # 模型返回的 JSON 无法解析时保留原字符串

class Message(BaseModel):
    role: Literal["system", "user", "assistant", "tool"]
    content: str | list[dict] | None = None     # list 预留给多模态
    tool_calls: list[ToolCall] | None = None
    tool_call_id: str | None = None
    name: str | None = None
```

一轮的输出 `turns.output = {"final": Message, "messages": [Message, ...]}`，其中 `messages` 是这一轮新增的全部 assistant 和 tool 消息。下一轮的历史 = 之前各轮 `input` + `output.messages` 依次拼接。

### 6.2 事件协议（`evalp-event/1`）

外层结构：

```json
{
  "seq": 17,                      // 由平台分配，同一会话内单调递增；llm.delta 没有 seq
  "turn_id": "trn_…",
  "ts": "2026-10-25T08:00:01.123Z",
  "type": "tool.call",
  "step_id": "s5",                // 同一个步骤的开始和结束事件共用同一个 step_id
  "parent_step_id": "s4",
  "payload": { … }
}
```

| type | 是否落库 | payload |
|---|---|---|
| `turn.start` | 是 | `{input: Message, history_len}` |
| `llm.request` | 是 | `{provider, model, params, messages, tools}`（超过 32KB 的部分转存为 blob） |
| `llm.delta` | **否**，只推送 | `{step_id, text?, tool_call_delta?}` |
| `llm.response` | 是 | `{content, tool_calls, finish_reason, usage:{prompt_tokens,completion_tokens}, latency_ms, ttft_ms, cost}` |
| `tool.call` | 是 | `{call_id, name, arguments}` |
| `tool.result` | 是 | `{call_id, name, output, is_error, latency_ms, mocked}` |
| `span.start` / `span.end` | 是 | `{name, attrs}` / `{name, attrs, latency_ms}`，代码型 agent 用于记录自定义步骤（如检索） |
| `log` | 是 | `{level, message}` |
| `message.assistant` | 是 | `{message: Message}`，本轮最终回复 |
| `error` | 是 | `{code, message, retriable}` |
| `turn.end` | 是 | `{status, output, usage, cost, latency_ms, ttft_ms}` |

**约束**：每一轮必须以 `turn.start` 开始、以 `turn.end` 结束；Runner 负责补齐缺失的结束事件（比如超时或异常时补写 `turn.end{status:"timeout"|"error"}`）。

**步骤签名**（用于对比时对齐，见 9.2）：`llm.response → "llm"`，`tool.call → "tool:{name}"`，`span.start → "span:{name}"`，`message.assistant → "final"`。

### 6.3 Adapter 接口

```python
class RunContext(BaseModel):
    session_id: str
    turn_id: str
    version: VersionView           # 已固化的 Spec + 资产读取接口
    seed: int | None
    variables: dict                # 用例或会话级变量，会覆盖 Spec 中的 variables
    tool_mocks: dict | None        # 评测用例里的工具 mock
    deadline: float                # monotonic 时间
    cancel: asyncio.Event

class AgentAdapter(ABC):
    @abstractmethod
    def run_turn(self, ctx: RunContext, history: list[Message],
                 user_input: Message) -> AsyncIterator[AgentEvent]: ...
    async def healthcheck(self) -> HealthResult: ...
    async def aclose(self) -> None: ...

def build_adapter(spec: AgentSpec) -> AgentAdapter:
    match spec:
        case ConfigSpec():                      return ConfigAdapter(spec)
        case CodeSpec(transport="http"):        return HttpAdapter(spec)
        case CodeSpec(transport="subprocess"):  return SubprocessAdapter(spec)
```

`Runner` 负责 Adapter 之外的通用逻辑：分配 seq、校验事件顺序、处理超时和取消（用 `asyncio.timeout` 包住迭代）、捕获异常转成 `error` 事件、补齐 `turn.end`、汇总 usage 和 cost。

### 6.4 ConfigAdapter

```python
async def run_turn(self, ctx, history, user_input):
    system = render_system_prompt(spec.prompts, ctx.variables, knowledge=load_inject(spec))
    messages = [Message(role="system", content=system), *history, user_input]
    tools = ToolSet.from_spec(spec.tools, mocks=ctx.tool_mocks)
    yield ev("turn.start", input=user_input, history_len=len(history))
    for step in range(spec.runtime.max_steps):
        sid = new_step_id()
        yield ev("llm.request", step_id=sid, messages=messages, tools=tools.schemas(), ...)
        async for chunk in llm.stream_chat(provider, model, messages, tools.schemas(), params):
            if chunk.delta: yield ev("llm.delta", step_id=sid, **chunk.delta)
        resp = llm.last_response              # 合并后的完整结果
        yield ev("llm.response", step_id=sid, **resp)
        assistant = resp.to_message(); messages.append(assistant)
        if not resp.tool_calls:
            yield ev("message.assistant", message=assistant)
            return                            # Runner 补写 turn.end
        calls = resp.tool_calls
        results = await (gather if spec.runtime.parallel_tool_calls else sequential)(
            tools.execute(c, timeout=spec.runtime.tool_timeout_s) for c in calls)
        for c, r in zip(calls, results):
            yield ev("tool.call", step_id=new_step_id(), parent_step_id=sid, ...)
            yield ev("tool.result", ...)
            messages.append(Message(role="tool", tool_call_id=c.id, content=r.as_text()))
    yield ev("error", code="MAX_STEPS_EXCEEDED", retriable=False)
```

- **prompt 渲染**：使用 Jinja2 沙箱环境，模板中可用的变量有 `variables`、`knowledge[name]`、`now`；引用了未定义的变量会报错（`StrictUndefined`）。
- **工具结果**：转为文本时，dict 用 `json.dumps(ensure_ascii=False)`；超过 16K 字符截断并标注 `[truncated]`。

### 6.5 HttpAdapter 协议（`evalp-agent/1`）

**请求** `POST {base_url}/evalp/run`

```json
{
  "protocol": "evalp-agent/1",
  "session_id": "ses_…", "turn_id": "trn_…",
  "history": [Message, ...],
  "input": Message,
  "params": { … },              // spec.params
  "variables": { … },
  "tool_mocks": { … } | null,
  "seed": 42,
  "deadline_ms": 300000
}
```

**响应**分两种接入等级，agent 可以按需选择：

| 等级 | Content-Type | 内容 |
|---|---|---|
| L1 最简 | `application/json` | `{"output": Message, "usage"?: {...}}`；平台自动补齐 `turn.start`、`message.assistant`、`turn.end` |
| L2 完整 | `application/x-ndjson` | 每行一个事件（不含 seq、turn_id、ts，由平台补齐），可包含 `llm.delta` |

- **取消**：平台断开连接，并尽力调用 `POST {base_url}/evalp/cancel {turn_id}`；
- **健康检查**：`GET {base_url}/evalp/health → {"ok":true,"protocol":"evalp-agent/1"}`；
- **HTTP 错误**：429、502、503、504 视为可重试错误，交给评测调度器重试；其他错误直接记为失败。

### 6.6 SubprocessAdapter

- 每轮启动一次 `command`（无状态）：把请求 JSON 写入 stdin 后关闭 stdin；从 stdout 逐行读取 NDJSON 事件（格式同 L2），stdout 只有一个 JSON 对象时按 L1 处理；
- stderr 按行转成 `log` 事件（level=warn）；
- 超时或取消时，用 psutil 终止整个进程树（Windows 上启动时设置 `CREATE_NEW_PROCESS_GROUP`）；
- 环境变量：继承平台进程的环境，叠加 `spec.subprocess.env`，并注入 `EVALP_SESSION_ID` 和 `EVALP_TURN_ID`。

### 6.8 LLM 客户端

- 基于 `AsyncOpenAI(base_url=…, api_key=…, timeout=…)`，每个 Provider 一个客户端实例，复用连接；
- 流式请求设置 `stream_options={"include_usage": True}`；服务端不返回 usage 时用 tiktoken 估算，并标记 `usage.estimated=true`；
- **重试**：对 429、500、502、503、504、超时、连接错误重试；指数退避，基础间隔 1s，倍数 2，加 ±20% 抖动，单次上限 30s，最多 4 次；优先遵守响应头中的 `Retry-After`；
- **限流**（`RateLimiter`，每个 Provider 一个）：
  - 并发信号量：`max_concurrency`；
  - RPM 令牌桶：每分钟补充 `rpm_limit` 个；
  - TPM 令牌桶：请求前按"prompt 估算 token + max_tokens"预扣，响应后按实际 usage 多退少补；
  - **优先级**：等待队列按优先级排序，交互请求（对话、双栏）高于重放，重放高于评测，避免评测压满时 UI 对话一直排队；
- **计费**：`cost = prompt_tokens × price_in + completion_tokens × price_out`（价格配置在 Provider 的 `models` 中，单位：元 / 百万 token）。

### 6.9 工具执行

| 类型 | 执行方式 |
|---|---|
| http | httpx 发请求；渲染 `body_template`；2xx 返回响应体（JSON 或文本），其他状态返回 `is_error=true` |
| python | 启动子进程 `{python} -m evalp.toolhost --entry mod:func`，stdin 传 JSON 参数，stdout 返回 JSON 结果；有超时；`workdir` 加入 `sys.path` |
| mock | 按 `responses` 顺序做参数子集匹配，都不匹配时使用 `default`，还没有则返回错误 |
| builtin `knowledge_search` | 知识资产按段落切块（≤500 字），jieba 分词后建立 BM25 索引（按修订哈希缓存在内存中），返回 top_k 条 `{source, chunk_id, text}` |

如果评测用例带了 `tool_mocks`，对应工具会被替换成 mock 实现，`tool.result.mocked=true`。

## 7. 会话与实时推送

### 7.1 执行一轮

```
POST /api/v1/sessions/{id}/turns   {"input": "…" | Message, "variables"?: {}, "wait"?: false}
→ 202 {"turn_id": "trn_…", "stream_url": "/api/v1/sessions/{id}/stream?after_seq=42"}
→ wait=true 时阻塞到本轮结束，返回 200 {turn}（供 MCP 的 chat 工具和 CLI 使用）
```

- 同一个会话同一时间只能执行一轮，会话处于 running 时返回 `409 SESSION_BUSY`；
- 历史由 SessionSvc 从 `turns` 表组装（见 6.1），Adapter 不访问数据库；
- 取消：`POST /turns/{id}/cancel` → 设置 `ctx.cancel` → Runner 写入 `turn.end{status:"cancelled"}`。

### 7.2 EventSink（事件写入）

```python
class EventSink:
    """每个会话一个实例，负责分配 seq、批量落库、发布到 EventBus。"""
    def __init__(self, session_id, start_seq): ...
    async def emit(self, ev: AgentEvent):
        if ev.type == "llm.delta":
            bus.publish(f"session:{sid}", ev.with_seq(None)); return
        ev = ev.with_seq(self._next())
        bus.publish(f"session:{sid}", ev)
        self._buf.append(ev)
        if len(self._buf) >= 100 or ev.type in ("turn.end", "error"):
            await self.flush()
    # 后台定时任务每 50ms 调用一次 flush()
    # flush：一个事务内批量 INSERT events，并 UPDATE sessions.last_seq
```

先发布、后落库，用户能更快看到输出；SSE 回放和实时之间的衔接靠 seq 去重（见 7.4），所以先后顺序不会导致重复或丢失。

### 7.3 EventBus

- 主题：`session:{id}`、`eval:{run_id}`、`compare:{id}`；
- 实现：`dict[topic, set[asyncio.Queue]]`，每个订阅者一个有界队列（容量 1000）；
- 订阅者处理太慢、队列满了时，直接断开该订阅者，前端带上 `Last-Event-ID` 自动重连，从数据库补齐。

### 7.4 SSE：先回放、再订阅

```python
async def stream(session_id, after_seq):
    q = bus.subscribe(f"session:{session_id}")      # 1. 先订阅，期间的实时事件先缓存在队列中
    last = after_seq
    for ev in repo.events_after(session_id, after_seq):   # 2. 从数据库回放
        yield sse(ev); last = ev.seq
    while True:                                     # 3. 消费实时事件
        ev = await q.get_with_heartbeat(15)         # 每 15s 发送一次 ": ping"
        if ev.seq is not None and ev.seq <= last: continue   # 去重
        yield sse(ev); last = ev.seq or last
```

SSE 帧格式：`id: {seq}`（delta 事件不带 id）、`event: {type}`、`data: {json}`。会话已结束、没有正在运行的轮次时，回放完会发送 `event: idle`，前端据此关闭连接。

## 8. 评测

### 8.1 发起评测

```json
POST /api/v1/evals
{
  "name": "v13 回归",
  "version_ids": ["ver_v12", "ver_v13"],        // 每个版本生成一个 EvalRun，同属一个批次
  "dataset": "asset://dataset/cs-regression@latest",
  "case_filter": {"tags": ["p0"]},
  "evaluators": [ … ],                          // 见 8.5
  "repeats": 3,
  "concurrency": 16,                            // 每个 Run 的并发上限；全局还受 worker 数和限流约束
  "seed": 42,
  "cache_policy": "reuse",
  "budget": {"max_cost": 20.0}
}
→ 201 {"batch_id": "evb_…", "runs": [{"id": "evr_…", "version_id": "…"}], "estimate": {"items": 600, "tokens": 1.8e6, "cost": 6.4}}
```

**成本预估**：同一个 agent 在这个数据集上有历史评测时，用历史的平均每条 token 数估算；没有历史时，按"input 估算 token × 3 + max_tokens × 0.5"粗略估算。参数 `dry_run=true` 时只返回预估结果，不真正创建。

### 8.2 状态机

**EvalRun**

```
queued ─▶ running ─▶ completed
            │  ▲         └─▶ completed_with_errors（有失败项）
            ▼  │
          paused        running/paused ─▶ cancelled
                        budget_exceeded ─▶ paused（reason=budget）
```

**EvalItem**

```
pending ─▶ running ─▶ scoring ─▶ done
              │                    
              ├─▶ pending（可重试的错误，attempts < 3，run_after 推迟）
              └─▶ failed ─(retry-failed)─▶ pending
pending/running ─▶ cancelled
cached：创建时命中缓存，直接进入 scoring
```

### 8.3 Scheduler

```python
class Scheduler:
    def __init__(self, workers: int = settings.global_concurrency):  # 默认 32
        self._claim_lock = asyncio.Lock()
        self._group_running: Counter[str] = Counter()          # 每个 run 当前正在执行的数量

    async def worker_loop(self):
        while not stopping:
            job = await self.claim()
            if not job: await self._wakeup.wait_for(1.0); continue
            try:    await HANDLERS[job.kind](job)                # eval_item / replay_turn / rescore
            except Retriable as e: await self.reschedule(job, backoff(job.attempts), e)
            except Exception as e: await self.fail(job, e)
            finally: self._group_running[job.group_id] -= 1

    async def claim(self):
        async with self._claim_lock:
            saturated = [g for g, n in self._group_running.items() if n >= limit_of(g)]
            job = repo.claim_job(exclude_groups=saturated + paused_groups())
            #  UPDATE jobs SET status='running', attempts=attempts+1, updated_at=:now
            #  WHERE id = (SELECT id FROM jobs WHERE status='pending' AND run_after<=:now
            #              AND group_id NOT IN (:excluded)
            #              ORDER BY priority DESC, created_at LIMIT 1)
            #  RETURNING *;
            if job: self._group_running[job.group_id] += 1
            return job
```

- **重启恢复**：启动时执行 `UPDATE jobs SET status='pending' WHERE status='running'`，并把对应 EvalItem 也重置为 pending，已经产生的会话标记为废弃（`sessions.status='error'`）；
- **暂停**：Run 进入 paused 后不再领取它的任务，正在执行的任务继续跑完；
- **取消**：未开始的任务置为 cancelled，正在执行的通过 `ctx.cancel` 中断；
- **预算**：每个 Item 完成后累加 cost，超过 `budget.max_cost` 时暂停这个 Run，并推送 `eval.budget_exceeded` 事件。

### 8.4 执行单元与缓存

```python
case_hash = sha256(canonical({"input": case.input, "variables": md.variables, "tool_mocks": md.tool_mocks}))
cache_key = sha256(f"{version.spec_hash}|{case_hash}|{repeat_idx}|{run.seed}")
```

- `expected` 和 `rubric` **不**计入 `case_hash`：只修改期望答案时，不需要重新运行 agent，只需要重新评分；
- **缓存命中**（`cache_policy=reuse`，并且存在相同 `cache_key`、状态为 done、`turn.end` 为 ok 的 Item）：新 Item 的 `session_id` 直接指向原来的会话，`reused_from_item_id` 记录来源，然后直接进入评分；
- **执行一个 Item**：创建 `Session(mode=eval)` → 按 `case.input.turns` 依次执行每一轮 → 任意一轮报错则整个 Item 失败（可重试的错误抛出 `Retriable`）→ 进入评分；
- **仅重新评分**：`POST /evals/{id}/rescore {evaluators?}` → 对比每个评估器的 `evaluator_hash`，只重新计算发生了变化的评估器。

### 8.5 评估器

所有评估器的输出都归一化为 `score ∈ [0,1]`、`passed: bool`、`reason`；配置项 `gate: true`（默认值；human 类型默认 false）表示这个评估器参与 Item 的通过判定。

| type | 配置 | 逻辑 |
|---|---|---|
| `exact_match` | `field`（final / 正则提取）、`normalize: [strip, lower, nfkc, punct]` | 规范化后与 `expected` 完全相等 |
| `contains` | `values`（为空时用 expected）、`mode: all\|any`、`negate` | 包含判断 |
| `regex` | `pattern`、`flags` | `re.search` |
| `json_schema` | `schema`、`extract: auto\|codeblock` | 从回复中提取 JSON 后做校验 |
| `trace` | `assert: {tool_called, tool_not_called, max_steps, max_latency_ms, max_tokens}` | 基于事件流做断言，检查 agent 的行为 |
| `llm_judge` | `provider`、`model`、`prompt`（资产引用）、`scale: [1,5]`、`pass_threshold`、`samples: 1` | 见下文 |
| `python` | `entry: mod:func`、`timeout_s` | 函数签名 `func(case, transcript) -> {score, passed, reason}`，通过 toolhost 子进程执行 |
| `human` | `scale`、`guideline` | 生成 `pending_human` 状态的评分，在 UI 中逐条打分 |

**LLM 评审**

- 评审 prompt 是普通的 prompt 资产，可用变量：`input`、`output`、`expected`、`rubric`、`transcript`（工具调用摘要）；
- 调用时设置 `response_format={"type":"json_object"}`，要求输出 `{"score": int, "reason": str}`；解析失败时重试 1 次，仍然失败则该评分记为 error（不计入通过判定，但计入错误率）；
- 每次评审调用都记录为一个 `Session(mode=judge)`，可以回看评审过程；
- `samples>1` 时调用多次取平均分；
- 平台内置默认评审 prompt 资产 `prompt/judge-default`，首次启动时自动创建。

### 8.6 汇总指标（`eval_runs.stats`）

```json
{
  "cases": 200, "items": 600, "done": 594, "failed": 6, "cached": 120,
  "pass_rate": 0.82,                      // 各用例通过率的平均值；用例通过率 = 通过的重复次数 / 重复次数
  "pass_at_k": {"1": 0.82, "3": 0.91},
  "flaky_cases": 17,                      // 0 < 用例通过率 < 1
  "evaluators": {"judge": {"mean": 0.78, "std": 0.21, "errors": 2}, "...": {}},
  "latency_ms": {"p50": 3200, "p95": 9100},
  "tokens": {"prompt": 1.2e6, "completion": 3.1e5},
  "cost": 6.12,
  "error_rate": 0.01,
  "by_tag": {"p0": {"pass_rate": 0.9, "cases": 50}}
}
```

### 8.7 评测对比

`GET /evals/compare?left=evr_a&right=evr_b&threshold=0.05`

1. 按 `case_key` 关联两次评测的用例。两侧数据集修订不同时返回警告；只出现在一侧的用例归入 `new` 或 `missing`；
2. 每个用例的分数 `s = 门禁评估器 score 平均值的重复均值`，差值 `Δ = s_R − s_L`；
3. 分类：`|Δ| < threshold` 为 unchanged；`Δ > 0` 为 improved；`Δ < 0` 为 regressed；任意一侧重复间标准差大于 0.3 时额外标记为 `flaky`；
4. 整体结论：
   - 平均 Δ，以及**配对 bootstrap** 95% 置信区间（对用例重采样 2000 次）；
   - 胜/平/负计数，加上符号检验（sign test）的 p 值；
   - 各项指标的差值：通过率、各评估器均值、p50/p95 延迟、token、成本；
5. 返回分页的用例明细：`{case_key, class, left:{score, item_ids}, right:{…}, delta, tags}`。默认排序：退化的在前，并按 |Δ| 从大到小。

## 9. 对比

### 9.1 CompareGroup

```json
POST /api/v1/compare
{"kind": "session", "mode": "live", "left": {"version_id": "ver_a"}, "right": {"version_id": "ver_b"}, "title": "…"}
{"kind": "session", "mode": "history", "left": {"session_id": "ses_x"}, "right": {"session_id": "ses_y"}}
{"kind": "eval",    "left": {"run_id": "evr_a"}, "right": {"run_id": "evr_b"}}
{"kind": "version", "left": {"version_id": "ver_a"}, "right": {"version_id": "ver_b"}}
```

- `live` 模式会自动创建两个 `Session(mode=chat)`，`left_ref` 和 `right_ref` 保存这两个会话的 id；
- 一期只支持两侧对比（左、右）。

### 9.2 会话对齐算法

1. **轮次对齐**：两侧都有 `pair_index`（live 模式）时按 `pair_index` 对齐，否则按 `idx` 对齐；
2. **步骤对齐**：对每一组对齐的轮次，按 6.2 节的规则生成两侧的步骤签名序列，例如：

```
L: [llm, tool:query_order, llm, final]
R: [llm, tool:query_order, tool:knowledge_search, llm, final]
```

   用 LCS 求出对齐结果（`difflib.SequenceMatcher` 的 opcodes），输出 `equal / insert / delete / replace` 片段；

3. **步骤内容 diff**：
   - 对齐的工具调用：参数做 JSON diff；结果做文本 diff；
   - 对齐的 `llm` 和 `final`：内容在前端用 diff-match-patch 按字符做 diff（适合中文）；
4. **指标**：每一轮两侧的 token、耗时、首 token 时间（TTFT）、步骤数、工具调用数、成本，以及它们的差值。

```json
GET /api/v1/compare/{id}/alignment
{
  "turns": [{
    "pair": 0,
    "left_turn": "trn_…", "right_turn": "trn_…",
    "steps": [
      {"op": "equal",  "left": "s1", "right": "s1", "sig": "llm"},
      {"op": "equal",  "left": "s2", "right": "s2", "sig": "tool:query_order", "args_diff": []},
      {"op": "insert", "right": "s3", "sig": "tool:knowledge_search"},
      {"op": "equal",  "left": "s3", "right": "s4", "sig": "llm"},
      {"op": "equal",  "left": "s4", "right": "s5", "sig": "final"}
    ],
    "metrics": {"left": {"latency_ms": 2100, "tokens": 1830}, "right": {"latency_ms": 3400, "tokens": 2410}}
  }]
}
```

前端在运行中会根据 SSE 事件**增量**计算对齐结果（算法同上，在 TS 中实现一份）；会话结束后以服务端的结果为准，并缓存。

### 9.3 双栏实时对话

```
POST /api/v1/compare/{id}/turns {"input": "…"}
  → 检查两侧会话都处于空闲状态，否则返回 409
  → pair_index = max(pair_index) + 1
  → asyncio.gather(session_svc.run_turn(L, input, pair_index), session_svc.run_turn(R, input, pair_index))
  → 202 {"pair_index": 3, "left_turn": "…", "right_turn": "…"}
```

- 前端同时订阅两个会话的 SSE，同一个 `pair_index` 的轮次在同一行显示，两侧高度对齐；
- 一侧出错不影响另一侧；
- "分叉"：可以只给其中一侧单独发送消息（这时 `pair_index` 为空），但之后再按 `pair_index` 对齐时，这条消息不参与对齐，在 UI 中标为"单侧消息"。

### 9.4 历史重放

```
POST /api/v1/sessions/{src}/replay {"target_version_id": "ver_b", "mode": "anchored" | "free", "turns"?: [0, 2]}
→ 201 {"session_id": "ses_new", "compare_id": "cmp_…"}
```

| 模式 | 第 k 轮的上下文 | 执行方式 | 适用场景 |
|---|---|---|---|
| `anchored` | 原会话第 0 到 k-1 轮的 input + output.messages | 各轮相互独立，作为 `replay_turn` 任务**并发**执行 | 精确比较单轮差异，排除前面轮次差异的累积影响 |
| `free` | 新会话自己前面各轮的消息 | 逐轮**串行**执行（前一个任务完成后才把下一轮加入队列） | 观察整段对话的走向 |

- 锚定模式下，新会话中的每一轮都会额外保存 `anchored_history_from: src_turn_id`，查看历史时以原会话的上下文为准；
- 完成后自动生成 `CompareGroup(kind=session, mode=replay)`。

## 10. 工作区同步

### 10.1 `.evalp.toml`（放在 agent 项目根目录，建议提交到 git）

```toml
[server]
url = "http://127.0.0.1:7860"

[agent]
name = "customer-support"        # 首次 push 时自动创建 agent
spec = "agent.yaml"
draft = "main"

[assets]                          # 本地文件 → 资产映射；支持 glob，{stem} 表示不带扩展名的文件名
"prompts/system.md"        = "prompt/cs-system"
"tools/*.yaml"             = "tool/{stem}"
"knowledge/*.md"           = "knowledge/{stem}"
"datasets/regression.jsonl" = "dataset/cs-regression"
```

本地状态文件 `.evalp/state.json`（应加入 `.gitignore`）记录 `agent_id`、`draft_id`、`draft_revision`，以及每个文件上次 push 时的哈希。

### 10.2 push 流程（CLI 或 MCP 进程在客户端执行）

1. 读取 `agent.yaml`，把其中的 `file:` 引用和 `[assets]` 中映射的文件，计算哈希后与 state 比较，只上传有变化的文件 → `POST /assets/{id}/revisions`（服务端按内容去重）；
2. 把 `file:prompts/system.md` 改写为 `asset://prompt/cs-system@latest`；
3. `PUT /drafts/{id} {spec, expected_revision}`：
   - 返回 409 `DRAFT_CONFLICT`：说明有人在 UI 里改过草稿，这时返回服务端草稿与本地 Spec 的 diff，提示用户执行 `evalp pull` 或 `evalp push --force`；
4. 更新 state。

### 10.3 pull 流程

拉取草稿 → 对每个 `asset://…@latest` 引用，如果它在 `[assets]` 中有映射，就下载内容写回本地文件，并把引用还原为 `file:`；没有映射的引用保持原样 → 写回 `agent.yaml`。

## 11. REST API

### 11.1 通用约定

- 前缀 `/api/v1`；请求和响应都是 JSON（UTF-8）；
- 鉴权：请求头 `Authorization: Bearer {token}`，token 来自 `{data_dir}/token`；Web UI 由同一服务提供，首次访问页面时服务端下发 HttpOnly、SameSite=Strict 的 Cookie；
- 分页：`?limit=50&cursor={上一页最后一条的 id}`，响应 `{"items": [...], "next_cursor": "…" | null}`；
- 乐观锁：写草稿时必须带 `expected_revision`；
- 错误格式：

```json
{"error": {"code": "DRAFT_CONFLICT", "message": "草稿已被修改（当前 revision=8）", "details": {"current_revision": 8}}}
```

### 11.2 错误码

| HTTP | code | 场景 |
|---|---|---|
| 400 | `VALIDATION_ERROR` | 请求或 Spec 校验失败，`details.errors` 给出字段路径 |
| 400 | `SPEC_INVALID` | Spec 的业务校验失败（Provider、模型或资产不存在） |
| 400 | `GIT_DIRTY` | 代码型 agent 工作区有未提交的改动，且不允许 dirty |
| 401 | `UNAUTHORIZED` | token 缺失或错误 |
| 404 | `NOT_FOUND` | 资源不存在 |
| 409 | `DRAFT_CONFLICT` | 草稿 revision 不一致 |
| 409 | `SESSION_BUSY` | 会话正在执行一轮 |
| 409 | `ASSET_IN_USE` | 被引用的资产不能硬删除 |
| 409 | `INVALID_STATE` | 状态机不允许这个操作（如对已完成的评测执行暂停） |
| 422 | `DATASET_PARSE_ERROR` | 数据集解析失败，`details.lines` 给出出错的行号 |
| 502 | `PROVIDER_ERROR` | 模型服务返回了不可重试的错误 |
| 502 | `AGENT_ERROR` | 代码型 agent 返回错误或违反协议 |
| 504 | `TIMEOUT` | 超时 |

### 11.3 主要接口明细

| 方法 | 路径 | 请求 | 响应 |
|---|---|---|---|
| POST | `/agents` | `{name, kind, description?, spec?}` | `{agent, draft}`（同时创建 main 草稿） |
| PUT | `/drafts/{id}` | `{spec, expected_revision}` | `{draft}` |
| POST | `/drafts/{id}/validate` | — | `{ok, errors[], warnings[], resolved_preview}` |
| POST | `/drafts/{id}/publish` | `{expected_revision, notes?}` | `{version, existed}` |
| GET | `/versions/diff` | `?left=&right=` | 见 4.5 |
| POST | `/assets` | `{kind, name, description?, content \| blob_upload_id, content_type, message?}` | `{asset, revision, existed}` |
| POST | `/assets/upload` | multipart（大文件） | `{blob_upload_id}` |
| POST | `/datasets/import` | `{name, content, format: jsonl\|csv, column_map?}` | `{asset, revision, case_count, warnings[]}` |
| POST | `/sessions` | `{version_id \| agent+tag, title?, variables?}` | `{session}` |
| POST | `/sessions/{id}/turns` | 见 7.1 | 见 7.1 |
| GET | `/sessions/{id}` | `?include=turns,events` | `{session, turns[], events[]?}` |
| GET | `/sessions/{id}/stream` | `?after_seq=` 或请求头 `Last-Event-ID` | SSE |
| POST | `/evals` | 见 8.1 | 见 8.1 |

| POST | `/evals/{id}/human-scores` | `[{item_id, evaluator_key, raw_score, reason}]` | `{updated}` |
| POST | `/workspace/push` | `{agent_name, draft_name, spec, files:[{path, asset, hash, content?}], expected_revision?}` | `{draft, uploaded[], skipped[]}` |

> MCP 和 CLI 的 push 由客户端读取本地文件后调用 `/workspace/push`，这个接口在服务端一次事务内完成 10.2 节的第 1 到 3 步。

### 14.2 关键组件

| 组件 | 要点 |

| `DraftEditor` | 左侧是根据 AgentSpec JSON Schema 生成的表单，右侧是 Monaco YAML 编辑器，两侧双向同步；输入时防抖调用 validate，错误标注在对应行；资产引用字段使用选择器（可选具体修订或 `@latest`）；底部显示"相对基础版本的改动数"和发布按钮 |

| `ChatPane` | 消息流式显示（处理 llm.delta）；每条 assistant 消息下可以展开工具调用卡片；底部显示指标条（tokens、耗时、TTFT、成本） |
| `TraceViewer` | 按 `step_id/parent_step_id` 构成的树；右侧是时间瀑布图；点击步骤查看 request/response 的 JSON（大 payload 按需从 blob 加载）；支持搜索 |
| `DualCompare` | 两个 ChatPane 并排，同一个 `pair_index` 的轮次在同一行；共享一个输入框（也可以切换为只发给某一侧）；"对齐视图"开关打开后，显示 9.2 节的步骤对齐结果，插入或删除的步骤高亮；文本差异按字符着色 |
| `EvalReport` | 顶部指标卡片；各评估器的分数分布（ECharts 直方图）；按标签分组的通过率；用例表（虚拟滚动，可按状态、标签、分数筛选，点击打开抽屉显示该用例每次重复的对话和评审理由） |
| `EvalCompare` | 结论卡片（Δ 和置信区间、胜平负、p 值）；分类页签（退化 / 改善 / 不稳定 / 新增 / 缺失）；用例两侧对照，可以一键"打开会话对比" |
| `AnnotateView` | 键盘快捷键（数字键打分，J/K 切换），评审标准常驻显示 |

### 14.3 SSE Hook

```ts
function useSessionStream(sessionId: string) {
  const [state, dispatch] = useReducer(sessionReducer, initial)   // 按 seq 去重，合并 delta
  useEffect(() => {
    let es: EventSource | null = null, last = 0, closed = false
    const open = () => {
      es = new EventSource(`/api/v1/sessions/${sessionId}/stream?after_seq=${last}`, { withCredentials: true })
      for (const t of EVENT_TYPES) es.addEventListener(t, (m: MessageEvent) => {
        const ev = JSON.parse(m.data); if (ev.seq) last = Math.max(last, ev.seq); dispatch(ev)
      })
      es.addEventListener('idle', () => { closed = true; es?.close() })
      es.onerror = () => { es?.close(); if (!closed) setTimeout(open, 1000) }   // 断线后从 last 继续
    }
    open(); return () => { closed = true; es?.close() }
  }, [sessionId])
  return state
}
```

当用户在 UI 中发出新一轮请求时，如果连接已经因为 idle 关闭，需要重新打开订阅。

## 16. 安全、配置与日志

### 16.1 安全

- 服务只绑定 `127.0.0.1`；如果用 `--host 0.0.0.0` 启动，会打印醒目警告，并强制所有请求都必须带 token；
- API token：首次启动时用 `secrets.token_urlsafe(32)` 生成，写入 `{data_dir}/token`（Windows 上通过 ACL 限制为仅当前用户可读）；
- Provider 密钥：存入 keyring（服务名 `evalp`，条目名 `provider:{id}`）；没有可用的钥匙串时，用 Fernet 加密后存入 `{data_dir}/secrets.enc`，加密密钥由机器标识派生；
- 脱敏：事件落库前，把请求头中的 `Authorization`、`X-*-Token`、`api_key` 等字段替换为 `***`；
- Python 工具和评估器：只执行用户自己配置的 entry；放在子进程中执行，有超时；UI 和文档会说明它们拥有本机权限；
- CORS：默认关闭，不允许跨域访问。

### 16.2 配置（`{data_dir}/config.toml`，环境变量 `EVALP_*` 可以覆盖）

```toml
[server]
host = "127.0.0.1"
port = 7860

[scheduler]
workers = 32                 # 全局并发上限
default_run_concurrency = 8
max_attempts = 3

[events]
flush_interval_ms = 50
flush_batch = 100
payload_inline_limit_kb = 32

[retention]
eval_sessions_days = 0       # 0 表示永久保留；大于 0 时，超期的评测会话由 GC 清理（报告汇总仍保留）
```

### 16.3 日志

- structlog 输出 JSON，写入 `{data_dir}/logs/evalp-YYYYMMDD.log`，保留 14 天；
- 每条日志都带 `request_id`，执行过程中还会带上 `session_id`、`turn_id`、`run_id`、`job_id`；
- `GET /health` 返回：`{ok, version, db_size, queue: {pending, running}, workers: {busy, total}, providers: [{name, inflight, rpm_left, tpm_left}]}`。
