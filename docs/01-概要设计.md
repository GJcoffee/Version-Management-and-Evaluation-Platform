## 1. 背景与目标

### 1.1 背景

开发 agent 的过程中，prompt、模型参数、工具和知识文件会被频繁修改，但目前缺少以下手段：

- 修改后无法确定哪一次改动导致效果变好或变差，旧版本也难以复现；
- 回归评测依赖手工逐条测试，速度慢，结果也不稳定；
- 两个版本在同一段对话里的表现差异，只能靠两个窗口来回切换人工比对；
- 开发主要在 IDE 和 agent 开发工具（Claude Code、Cursor 等）里进行，需要切换到另一个系统才能评测，流程是断开的。

### 1.2 目标

建设一个**本地运行**的 agent 版本管理与评测平台，满足以下要求：

1. **草稿与版本**：草稿可以随意修改，发布后生成不可变版本，任何结果都能追溯到具体版本并复现。
2. **资产管理**：prompt 模板、工具定义、知识文件、评测数据集统一管理，资产本身也有修订历史。
3. **并发评测**：对一个或多个版本并发跑数据集，支持多次重复、限流、断点续跑和结果缓存。
4. **版本对话**：可以选定任意版本发起对话，并查看完整的执行轨迹（trace）。
5. **对比**：
   - 两个版本的配置差异对比；
   - 两次评测的逐 case 对比；
   - 两个**运行中**的对话实时并排对比（同一输入同时发给两个版本）；
   - 两个**历史**会话对比；
   - 把历史会话放到另一个版本上重放，再做对比。
6. **工具接入**：通过 MCP Server、CLI 和 REST API，让 agent 开发工具能直接完成编辑草稿、发版、跑评测、读报告等操作。
7. **两类 agent 都支持**：配置型 agent 由平台执行；代码型 agent 通过 HTTP 或子进程接入。

### 1.3 非目标（一期不做）

- 多用户、多租户、权限体系（只做本机单用户）；
- 云端部署和分布式 worker；
- 模型训练和微调；
- OpenAI 兼容协议以外的私有模型协议（预留 Provider 扩展点，不在一期实现）。

## 2. 术语

| 术语 | 说明 |
|---|---|
| Agent | 一个被管理的智能体，下挂草稿、版本、会话、评测 |
| AgentSpec | 描述一个 agent 的结构化配置，分配置型（`config`）和代码型（`code`）两种 |
| Draft（草稿） | 可变的 AgentSpec 工作副本，记录基于哪个版本创建 |
| Version（版本） | 草稿发布后生成的不可变快照，包含解析后的 Spec 和内容哈希 `spec_hash` |
| Asset（资产） | 可复用的内容：prompt、tool、knowledge、dataset、file |
| AssetRevision | 资产的一次不可变修订，按内容哈希去重 |
| Dataset / EvalCase | 评测数据集，以及其中的单条用例（用 `case_key` 跨修订标识同一条用例） |
| EvalRun | 一次评测：版本 × 数据集修订 × 评估器 × 重复次数 |
| EvalItem | 评测的最小执行单元：用例 × 第几次重复 |
| Session（会话） | 一次多轮运行，绑定一个版本，用途包括对话、评测和重放 |
| Turn（轮次） | 会话中的一轮：一条用户输入及 agent 的完整响应 |
| Event（事件） | 一轮内部的标准化步骤记录（LLM 调用、工具调用、输出等），是 trace 的组成单位 |
| CompareGroup | 一组保存下来的对比关系（两个会话或两次评测） |
| Adapter | 把不同形态的 agent 统一成"输入 → 事件流"的适配层 |

## 4. 核心使用场景

### 场景 A：在 IDE 里改 prompt，发版并跑回归评测

1. 开发者在 agent 项目目录下修改 `agent.yaml` 和 `prompts/system.md`；
2. 让 Claude Code 调用 MCP 工具 `push_draft`，把本地文件同步成平台草稿；
3. 调用 `publish_version`，生成版本 v13；
4. 调用 `run_eval(version=v13, dataset=regression, baseline=v12)`；
5. 评测结束后，调用 `get_eval_compare` 拿到"退化 3 条、改善 7 条"的结论和对应 case 的 trace 摘要；
6. Claude Code 根据退化的 case 继续修改 prompt，重复以上步骤。

### 场景 B：双栏实时对比

1. 在 Web UI 中选择 v12 和 v13，进入双栏对话；
2. 输入一条消息，两个版本同时流式输出；
3. 每栏底部显示本轮的 token、耗时、工具调用次数；展开 trace 后，按步骤对齐展示两边的差异；
4. 对话结束后保存为对比记录，以后可以回看。

### 场景 C：用历史会话验证新版本

1. 打开一条线上反馈有问题的历史会话（v12）；
2. 选择"在 v13 上重放"，有两种模式：
   - **锚定模式**：每一轮都使用原会话的历史上下文，只比较 v13 在该轮的输出，适合精确定位单轮差异；
   - **自由模式**：只复用原会话的用户输入，v13 用自己的输出作为后续上下文，适合观察整体走向；
3. 重放完成后自动进入历史对比视图。

## 5. 总体架构

```
┌───────────────────────────── 客户端 ─────────────────────────────┐
│  Web UI (React)          Claude Code / Cursor          终端/CI    │
│      │                         │ stdio                     │      │
│      │                   evalp mcp (MCP Server)        evalp CLI  │
└──────┼─────────────────────────┼───────────────────────────┼──────┘
       │ REST + SSE              │ REST                      │ REST
┌──────┴─────────────────────────┴───────────────────────────┴──────┐
│                    evalp serve（单进程，FastAPI）                   │
│ ┌───────────── API 层：路由 / 鉴权 / 校验 / SSE ─────────────────┐ │
│ ├───────────── Service 层 ──────────────────────────────────────┤ │
│ │ AgentSvc  DraftSvc  VersionSvc  AssetSvc  DatasetSvc          │ │
│ │ SessionSvc  EvalSvc  CompareSvc  ProviderSvc  WorkspaceSvc    │ │
│ ├───────────── 运行时 ──────────────────────────────────────────┤ │
│ │ Runner ── Adapter: ConfigAdapter | HttpAdapter | SubprocessAdapter │
│ │ ToolExecutor (http / python / mock / builtin)                  │ │
│ │ LLMClient (OpenAI 兼容) + RateLimiter                          │ │
│ │ Scheduler (任务队列 + Worker 池)    EventBus (进程内发布订阅)   │ │
│ ├───────────── 存储层 ──────────────────────────────────────────┤ │
│ │ Repository (SQLAlchemy)           BlobStore (内容寻址)         │ │
│ └────────────────────────────────────────────────────────────────┘ │
└──────────────┬─────────────────────────────────────┬──────────────┘
          SQLite (WAL)                     ~/.evalp/blobs/ab/cdef…
                                                     │
                         ┌───────────────────────────┴─────────┐
                         │  外部：OpenAI 兼容模型服务            │
                         │       代码型 agent（HTTP / 子进程）   │
                         └─────────────────────────────────────┘
```

**分层原则**

- 所有入口（UI、MCP、CLI）都只通过 REST 调用同一个服务进程。MCP 和 CLI 是"薄客户端"，自己不访问数据库，这样可以避免多进程同时写 SQLite。
- Service 层不感知 HTTP，Runner 不感知具体的 agent 形态，存储层不感知业务。
- 一期在单进程内用 asyncio 处理并发；Scheduler 抽象成接口，以后可以替换为多进程或分布式实现。

## 6. 关键设计决策

| # | 决策 | 理由 | 代价 |
|---|---|---|---|
| D1 | **版本不可变，用内容哈希标识** | 结果可复现；相同内容的版本自动去重；评测缓存可以直接以哈希为 key | 每次发布都需要先把引用固化，再做规范化计算 |
| D2 | **资产按内容寻址存储，引用固化到修订** | 草稿里可以写 `@latest`，发布时固化成具体修订，避免资产后续修改影响历史版本 | 需要做引用计数和垃圾回收 |
| D3 | **一切运行统一成事件流** | 对话、评测、重放共用一套 trace 模型；实时视图和历史视图共用一套渲染和对比逻辑 | 需要定义清楚并维护好事件协议 |
| D4 | **SSE 采用"先回放、再订阅"** | 前端只需按 `after_seq` 订阅，不用区分会话是正在运行还是已经结束 | 回放和实时之间的衔接需要按序号去重 |
| D5 | **评测的每个执行单元都是一个会话** | 评测 trace 直接复用会话查看器；评测里的 case 可以一键"在对话中打开" | 会话表数据量较大，需要加索引并支持按用途过滤 |
| D6 | **Adapter 协议采用无状态的单轮调用** | 每次调用都传入完整历史，重放和锚定对比实现起来很简单；代码型 agent 接入门槛低 | 长对话每次都要传完整历史，开销稍大（本地场景可以接受） |
| D7 | **SQLite WAL + 单写进程** | 零运维、一个文件即可备份；单进程写入时并发足够 | 横向扩展受限（一期是本地场景，不需要） |
| D8 | **MCP 与 CLI 作为 REST 的薄客户端** | 只有一处业务逻辑；IDE 侧可以随时启动和停止 | 使用 MCP 和 CLI 前需要先启动 `evalp serve`（CLI 可以自动拉起） |
| D9 | **工作区文件与草稿双向同步** | agent 开发工具最擅长改文件，让它们改文件，而不是调用复杂接口 | 需要处理冲突（用乐观锁 + 修订号解决） |

## 7. 领域模型

```
Provider 1───* (被 AgentSpec 中的 model.provider 引用)

Agent 1───* Draft
  │  1───* Version ───* VersionTag
  │            │ * 引用 *
  │            └────────── AssetRevision *───1 Asset
  │
  ├── 1───* Session 1───* Turn 1───* Event
  │             ▲  (mode = chat | eval | replay | judge)
  │             │
  └── 1───* EvalRun 1───* EvalItem 1───1 Session
                │              └──* EvalScore
                ├── * Evaluator 配置
                └── 1 DatasetRevision(= AssetRevision, kind=dataset) 1───* EvalCase

CompareGroup ── 左侧引用 / 右侧引用（会话或评测）
EvalBatch 1───* EvalRun（一次发起多个版本的评测）
Job（Scheduler 任务表，指向 EvalItem 或重放步骤）
```

**关键约束**

- 版本一旦写入就不再修改；`(agent_id, spec_hash)` 唯一。
- 版本对资产的引用只能指向具体的 AssetRevision，不允许指向 `latest`。
- 会话绑定 `version_id` 后不能修改。
- 同一个数据集，不同修订中的用例通过 `case_key` 对应，用于跨修订对比。

## 9. 关键流程

### 9.1 发布版本

```
客户端 → POST /drafts/{id}/publish {expected_revision}
DraftSvc: 乐观锁检查 → 校验 Spec（JSON Schema + 业务规则）
        → 固化引用（asset@latest → asset@rev_n）
        → 代码型：采集 git commit 和工作区是否有未提交改动（dirty）
        → 规范化（canonical JSON）→ sha256 = spec_hash
        → 已存在相同哈希？ 是：返回已有版本(200, existed=true)
                            否：写入 Version(seq+1)，更新 Draft.base_version_id
```

### 9.2 执行一轮对话

```
POST /sessions/{id}/turns {input}
SessionSvc: 写入 Turn(status=running)；分配事件序号
          → Runner.run_turn(version.spec, history, input)
              → Adapter 产出事件流 ─┬─ 持久化（llm.delta 只推送，不落库）
                                    └─ EventBus.publish(session:{id})
          → 写入 turn.end（用量、耗时、状态）
GET /sessions/{id}/stream?after_seq=N
          → 从数据库回放 seq>N 的事件 → 切换为实时订阅（按 seq 去重）
```

### 9.3 并发评测

```
POST /evals {version_ids[], dataset_rev, evaluators[], repeats, concurrency}
EvalSvc: 每个版本生成一个 EvalRun（同一批次）→ 生成 用例数×N 个 EvalItem → 入队 Job
Scheduler(Worker 池):
  取任务 → 查缓存(cache_key) → 命中：复用结果
                             → 未命中：限流令牌 → 创建 Session(mode=eval) → 执行
        → 执行评估器 → 写入 EvalScore → 更新 Item 状态 → 推送进度事件
全部完成 → 汇总指标 → Run.status=completed
进程重启 → 把状态为 running 的 Job 重置为 pending，从断点继续
```

### 9.4 双栏实时对比

```
POST /compare {kind:"session", left_version, right_version, mode:"live"}
  → 创建两个会话 + CompareGroup
POST /compare/{id}/turns {input}
  → 两个会话并发执行同一输入（共用 pair_index）
前端同时订阅两个会话的 SSE；按 pair_index 对齐轮次，用 LCS 对齐步骤
```

### 9.5 历史重放

```
POST /sessions/{src}/replay {target_version, mode: anchored|free}
  anchored：第 k 轮的上下文 = 原会话前 k-1 轮的完整消息
  free：    第 k 轮的上下文 = 新会话自己前 k-1 轮的消息
  → 新建 Session(mode=replay, source_session_id=src)
  → 逐轮执行（重放步骤作为 Job 进入队列，受统一限流约束）
  → 自动创建 CompareGroup(mode=history)
```

## 11. 非功能需求

| 类别 | 指标/要求 |
|---|---|
| 性能 | 单机评测支持并发数 1–128（默认 8）；平台自身开销 < 50ms/轮（不含模型耗时）；1 万条用例的评测报告首屏 < 2s（服务端分页 + 前端虚拟列表） |
| 实时性 | 流式输出从模型返回到 UI 显示的延迟 < 200ms |
| 可靠性 | 进程崩溃后评测能从断点继续；模型返回 429 或 5xx 时自动退避重试；单个 case 失败不影响整个评测 |
| 可复现 | 版本、数据集修订、评估器配置、seed 都会落库；同一个 `cache_key` 的结果可以复用 |
| 安全 | 只监听 127.0.0.1；本地 API token；Provider 密钥存入系统钥匙串（无钥匙串时存为权限 600 的加密文件）；trace 展示时对密钥脱敏 |
| 可维护 | 数据库迁移用 Alembic；后端核心模块单测覆盖率 ≥ 70%；Adapter 有协议契约测试 |
| 可观测 | 结构化日志（JSON，按天滚动）；`/health` 返回队列深度、worker 状态、各 Provider 限流状态 |
| 易用 | 安装后 `evalp serve` 一条命令即可启动；首次启动时引导配置 Provider |
| 兼容 | Windows / macOS / Linux；Python ≥ 3.11；Chrome / Edge 最新两个大版本 |

## 12. 部署与运行

- 安装：`pip install evalp`（前端构建产物打包进 wheel，由 FastAPI 以静态文件形式提供）；
- 启动：`evalp serve [--port 7860] [--data-dir ~/.evalp]`；
- 数据目录：

```
~/.evalp/
├── evalp.db            # SQLite（WAL）
├── blobs/ab/cdef…      # 内容寻址存储
├── logs/
├── token               # 本地 API token（权限 600）
└── config.toml         # 端口、并发等全局配置
```

- IDE 接入：在 Claude Code、Cursor 的 MCP 配置中添加命令 `evalp mcp`；
- 备份：停止服务后复制整个数据目录。

## 13. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 模型输出不稳定，导致对比结论被噪声干扰 | 误判版本优劣 | 默认重复 3 次；标记"不稳定"用例；报告给出 bootstrap 置信区间 |
| LLM 评审本身有偏差 | 分数不可靠 | 评审 prompt 也作为资产做版本管理；支持人工抽检；评审输出要求附理由 |
| SQLite 在高并发写入时出现锁竞争 | 吞吐下降 | 单写连接 + 批量写事件（每 50ms 或 100 条刷一次）；流式增量事件不落库 |
| 代码型 agent 不按协议输出 | trace 缺失 | 提供 `evalp-sdk` 辅助库和协议契约测试命令 `evalp adapter check` |
| Python 工具执行任意代码 | 本机安全风险 | 只执行用户自己登记的模块；子进程执行 + 超时；UI 明确提示 |
| 评测成本失控 | 产生意外费用 | 发起评测前预估 token 和成本；为每次评测设置预算上限，超出后自动暂停 |
